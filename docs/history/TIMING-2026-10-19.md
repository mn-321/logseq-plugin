Plugin Test Graph on the Mac. Each page opened 3 times; the number is the middle run, in milliseconds after Logseq's own page title appears. Under ~100 ms reads as "with the page"; around 1 s is a visible pop-in.

| Always-shown title buttons | all | 0 |
| Date boxes and tense | Priya, Atlas | 0 |
| Date tense / date boxes on the Journals list | Journals | 130 / 670 |
| This page marked in references | Journals | 670 |
| Two-way rows | Priya / Atlas | 910 / 1170 |
| Journal day summary | Journals | 1110 |

For comparison, Logseq's own Linked references arrive 140 to 530 ms after the title.

## Where the time goes (second round of measuring, same day)
- A database look-up takes 10 to 30 ms when Logseq is idle, from the plugin too (13 ms for a small one).
- Right after a page change Logseq is busy loading the new page for about half a second: a look-up sent then takes 300 to 800 ms to come back, and look-ups queue behind each other until about 1.3 s.
- `getCurrentPageBlocksTree` sent 0.4 s after the page change took 0.68 s; `refreshCues` waits for it before anything else.
- `loadPageKind` (shape box, tag line, inherited fields, alias) asks about eight questions one after another; started at the page change it took 2.2 s, on a quiet page 0.23 s.
- On every page change the plugin first waits a fixed 300 ms (`scheduleRefresh(300)`, `schedulePageKind(300)`; two-way waits 150 ms).
- `refreshCues` draws nothing until all its look-ups finish (one `Promise.all`), so its extras arrive together, as late as the slowest.
- Logseq's own screen work after a page change is small (about 0.3 s of busy frames, over by 0.6 s), so the wait is the database, not drawing.

## Fixes (0.4.150)
1. Start on page change without the fixed wait.
2. Ask the questions that don't depend on each other at the same time, and draw each extra as soon as its own answer is back.
3. Read the whole-graph lists again on a page change only when something changed since they were read (they were read fresh on every page change, which held up the shape box).
4. Remember each page's answers: going back to a page draws its extras at once from memory, then checks them quietly.

## After (measured 2026-10-19, 0.4.150, same graph and method)
First visit = the plugin's memory of the page emptied before the visit, in a warmed-up app. Back again = the page was seen before this session.

| Folded block cue | Atlas | 1510 | 1250 to 2000 | 0 |

Jumps (Chrome's layout-shift record: how far the page's content moves after the title is drawn). Logseq's own drawing moves things in the first 0.2 to 0.3 s on every visit (for example 280 px on Priya, 330 px on Meeting). On a first visit the extras still push the page down when they arrive (Priya's references move 680 px at about 0.75 s when the two-way rows land; Meeting moves 670 px when the shape box lands). On a page seen before, those late jumps are gone: the extras arrive with Logseq's own content, inside its first jump.

What is left: on a first visit the database is busy loading the page for the first half second, so an extra that needs a look-up can't arrive much before 0.6 s. The folded block cue still waits for the page's whole block tree (Logseq's `getCurrentPageBlocksTree`), the slowest call.
