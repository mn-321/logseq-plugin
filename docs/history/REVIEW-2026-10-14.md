# Quick review of DB Refinements 0.2.156 (2026-10-14)

Read-only review of the copy on A's Mac (main.js, package.json, README, GUIDE, HANDOFF). Nothing was changed. Ranked by how likely each is to confuse you or someone using the plugin.

## Things that would confuse

1. **The plugin quietly writes to your notes, in every graph.** "Fill dates automatically" is on by default, for the tags Occurrence and Results, and "Only in these graphs" is empty, which means all graphs, Work included (HANDOFF says this was allowed on 2026-10-13). Everything else in the plugin only changes how things look, so this is the one part that can change your data without you noticing.
   *Recommendation:* move it to its own small plugin (see below). Until then, at least list your graph names in "Only in these graphs".

2. **The README contradicts itself about the version.** Its first line says "Version 0.2.148"; the real version is 0.2.156. The history has no notes for 0.2.149 or 0.2.153. The Appearance table, which is meant to describe the plugin as it is today, has no row for the newest looks: grey property names, the light grey field behind property lists, and the "#" tab names with the "points here" mark on records.
   *Recommendation:* fix the first line, add the missing rows, and move the 300 lines of version notes into a separate CHANGELOG so the README is just "what it does now".

3. **Five plugin items on every bullet's right-click menu, whatever the block is.** "Fold all results", "Unfold all results" and "Choose properties shown in this list" only do something on a query or a list of records; "Copy styling details (troubleshooting)" is a developer tool. On an ordinary block they just say "nothing here".
   *Recommendation:* keep "Copy children to new page" in the menu and move the rest to the command palette only (they are already there).

4. **The same command has two names.** The command palette says "Copy block and children to new page", the right-click menu says "Copy children to new page". Next to the separate "Copy as Rich Text" plugin, "Copy…" is also easy to mix up: one makes a new page, the other copies text for outside readers.
   *Recommendation:* one name everywhere, and one that says what it does, e.g. "Move a copy of this branch to a new page" or "Make a page from this block".

5. **Settings descriptions lag behind what the settings now do.** "Plainer properties" describes the "name: value" row, but it now also turns property names grey and puts the grey field behind property lists. "Show how records are linked" now also controls the tag-tab marks. You would not know which switch to turn off.
   *Recommendation:* rewrite those two descriptions.

6. **Two copies of the plugin, and a leftover file.** The copy in the project's shared folder is older than the one on your Mac (339 KB vs 347 KB), and the Mac folder has a 318 KB `main.js.orig` next to `main.js`. Easy to open or zip the wrong one.
   *Recommendation:* delete `main.js.orig` (it is in git history anyway) and either keep the shared copy in step or mark it as a snapshot.

7. **The version number has stopped meaning much.** 156 small builds all under 0.2, while HANDOFF says 1.0 was due after "a quiet week of use in Work". Since then 15 more versions have gone in.
   *Recommendation:* call the current state 1.0.0 once you are happy with the look, then 1.0.1 for fixes and 1.1.0 for new features.

## Smaller gaps

- A few things have no off switch while everything else does: the Search button in the right sidebar, links inside a reference opening their own page, and page labels dropping a trailing "#tag".
- The settings heading "Right sidebar" also holds "Quiet these sidebar and toolbar items", which is about the left sidebar and toolbar.
- Some settings apply at once and some need a plugin reload. The panel says which, but only in small print; a reload message does appear when needed.
- HANDOFF's "Known loose ends" says Cmd+T only works on ordinary pages through "Set property"; the README says it now uses Logseq's own "Set tags". One of them is out of date.
- Everything was tested in light mode only (per project notes); dark mode is unchecked for the newer greys.

## What should be a separate plugin

**Yes, split these two:**

- **Journal-day dates** (auto-fill and the "Fill missing dates" command). It writes data, it is tied to your own tags (Occurrence, Results), and it has nothing to do with readability. As its own plugin you can switch it on per graph, and a look-only plugin can never touch your notes.
- **Search** (tidier rows, roomier window, details on each result, grouping, the preview panel and its trial editor, the typed filters, sidebar search). It is about a third of the code and seven settings, it is a different part of the app, and it is the part most likely to break when Logseq updates its search window. Splitting it means a search problem can be turned off without losing the rest, and the main settings list gets much shorter.

**Could go either way:** the writing helpers (Link selected text, Open selected text as page, Copy children to new page, Add tags). They are small and harmless; splitting them gains little unless the settings list feels crowded.

**Keep together:** everything that changes how pages, links, properties, references, dates and the sidebar look. That is the plugin's real purpose, and those parts share one set of colours and rules.

The Copy as Rich Text plugin is already separate and only overlaps on the word "Copy" (point 4).
