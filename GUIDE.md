# Guide: working on this plugin and on the graph from the command line

Written 2026-10-12 from what the audit, the safety round and the readiness review learned the hard way; updated 2026-10-16 after the cleanup that split `main.js` into parts (0.4.38 to 0.4.61), 2026-10-18 at 0.4.131, and 2026-10-24 at 0.4.381 (the machine, the tools and the parts as they are now). This file is for working on the plugin and is not part of the release zip. It is the standing advice: how the code is built, Logseq 2.0.2's quirks, the development loop and the command line. What each part is and which layer it belongs to is `docs/STATE.md`; the layers themselves are `docs/LAYERS.md`; the owner's rulings and what was tried and rejected are in `docs/history/DECISIONS-AND-RULINGS-2026-10-24.md`; older records are in `docs/history/`. Everything here was checked against Logseq 2.0.2 (DB graphs); re-check after an update.

## Part 1: the plugin

### Where the code is

- `loader.js` is Logseq's starting file; it loads `main.js` with a fresh timestamp so a reload picks up edits.
- `main.js` is the engine (about 500 lines): the screen watcher, the database round, `sendStyle`, the hooks the parts register with, the command register's palette and shortcut wiring, the self-check after a Logseq update, `main()` and the part loader. It knows nothing about pages, blocks or tags: that is the model's. Before it starts, it loads every file in `PART_FILES`, in order, with a fresh timestamp too. `RESTING_FILES` lists the parts kept in `parts/` but never loaded; `tools/check.sh` fails when a file in `parts/` is in neither list.
- `parts/shared.js` is loaded first: the kit (layer 2 of `docs/LAYERS.md`: the one pop-up, dialog, field, buttons, tick box, picking bar, hover card, Undo arrow, icon list, `el()` and `esc()`) and the helpers every part uses (settings, warnings, clean-up, the screen door `core.screen`). Its header is the written contract between the files: what it provides, what every other part must do, and the load order. Read that header before writing a part.
- `parts/model.js` is loaded second (0.4.164): the Logseq model, the one place that reads and writes the graph and knows what a page, block, tag, property, journal day and link are in a DB graph (`readableTitle`, `propSchema`, `propPages`, `fieldsOf`, `parseDay`, `linksInto`, `nodeValues`, `CHECKED_WITH`, `screenChecks` and the rest). Every other part takes these from `core.provided`; a change to how Logseq stores something lands here. Since 0.4.226 no other part asks the database itself, and `tools/leaning-test.js` keeps it that way.
- `parts/diagnostics.js` holds the troubleshooting tools (Check what the plugin finds on this page, Measuring, Copy performance report, Copy styling details of this block, Copy warnings, Take the tour). It reads the core's state through `window.refinementCore`.
- Every other loaded part is one feature or one piece of the page, standing on its own (`tools/parts-apart-test.js` boots the plugin with each left out). `docs/STATE.md` lists them by layer with their settings, keys and tests. A feature that is several files shares one object between them (`window.refinementTagMap` for the tag map's three, `window.refinementProposals` for the proposals' four).
- The settings window (`parts/settings-panel.js`) gathers sections by the `group` and `rank` their headings carry; a heading that names no group lands in Other. A new section wants a caption in the group's `legend` and a zone in its picture too.
- Every part is wrapped in its own scope, pushes `{ name, schema, provide?, start, ready?, commands?, moved?, stop }` onto `window.refinementParts`, and has its own clean-up list (and, where it cleans Logseq's window, its own stop key), made with `shared.lifecycle(…)`. `main()` runs every part's `provide(core)`, then every `start()` (take the others' things, register with the core), then every `ready()` (start what draws on screen, once every part has started), and registers the palette commands the parts declare; it starts nothing by name.
- Only one session at a time should edit a file; make small in-place edits and re-read the file first.

### What goes in the release zip

Only what Logseq needs and what a reader needs: `package.json`, `loader.js`, `main.js`, `parts/*.js`, `README.md` and `CHANGELOG.md`, inside a folder named `logseq-db-refinements`. `tools/`, the work notes (`GUIDE.md`, `CLAUDE.md`, `docs/`) and `test/` stay out. Since 0.4.280 the release is made on GitHub: every version commit gets a tag `v0.4.N`, pushed (`git tag v0.4.N && git push origin v0.4.N`), and `.github/workflows/publish.yml` builds the zip and attaches it to a GitHub Release, which Logseq's **Install plugin from GitHub release** installs (with the **effect** box ticked; see the README's Install). `sh tools/release.sh` still builds the same zip locally, into `~/logseq-plugin-archive/releases/`, after running the checks; that folder did not exist on the Mac on 2026-10-24, and no zip has been handed over by hand since the GitHub releases began.

### How the plugin is built, and the rules that keep it that way

- **One screen watcher.** `watchDomEarly(fn)` runs `fn(doc, records)` on every change Logseq makes, before paint; `watchDom(fn)` runs `fn(doc)` once in the next frame. Both live in `main.js` and are published on `window.refinementCore`; a part reaches them through the kit's screen door (`core.screen`). Put flash-prone work (citations, the title's corner, the two-way rows' room) in the early pass and everything else in the frame pass. Never add a `MutationObserver` of your own; the two exceptions run only while they are needed: the kit's Undo arrows (`watchUndos` in `parts/shared.js`, while an arrow is waiting) and the tour's recorder in `parts/diagnostics.js` (while a stop is measured).
- **One database round.** Anything that reads the graph after an edit registers with `core.onDbRound(name, fn, { scope, before })`: scope `'page'` (the default) runs after every round, `'graph'` only when the whole-graph lists fall due (every 30 s while you type, once more after you stop), and `before()` cancels a look-up of the job's own still waiting from a page change. `runDbWork` in `main.js` runs the graph jobs, then the page jobs, in the order the parts registered them; it knows no job by name, and never a timer of its own. Whole-graph look-ups go through `graphWide(name, load)`, which remembers the answer for the session until the graph changes.
- **Marks, not generated stylesheets.** What the database says is written onto the elements as `data-refinement-*` attributes or `refinement-*` classes, and a fixed stylesheet in the part draws from them. When you add a mark: name it in the part's own `leaves` (the `lifecycle(…)` call at the top of its file: its elements, the attributes it sets on Logseq's elements, a `reset` for anything else), so a new copy of the plugin sweeps it; remove it in the part's clean-up, and diff old and new sets each pass (see `updateCueMarks` in `parts/links.js`) so nothing is written twice.
- **Clean-up for everything.** Every part registers its undo with its own `onUnload`; every Logseq hook's "off" function goes through `onUnload` too. `runUnloadTasks` runs a part's steps in reverse, `main()` runs every part's, and a new copy of the plugin runs the previous copy's clean-up (`takeOverFromEarlierCopy`, from `shared.lifecycle`) and sweeps strays. After a change, three reloads in a row must leave one of everything (count with **Check what the plugin finds**, in the troubleshooting box).
- **The core's hooks.** The core listens to Logseq once for page changes, database changes and settings changes, does its own housekeeping (its caches, the database round, the reload note), and then runs what the parts registered in their `start()`: `core.onPageChange(fn)`, `core.onDatabaseChange(fn)` (given the changed blocks) and `core.onSettingsChange(fn)` (given the settings now and before). A part that must act on those events registers there rather than being named in `main()`; a part that needs a hook of its own (a timer of its own, a graph change) still takes it from `logseq.*` through its `onUnload`.
- **Stylesheets.** Send a stylesheet only when its text changed (`sendStyle`); Logseq re-lays out the page on every send. An empty stylesheet is ignored by Logseq, so send a comment (`orNoRules`) to clear one. Declare tokens on `:root, body`: Logseq defines its theme variables on `body`, and a token on `:root` that refers to them resolves to nothing. Each part's stylesheets are template strings in the part, sent through the core's `sendStyle`; a `provideStyle` key is part of the plugin's contract with the owner's settings file and never changes.
- **One scale.** Use the kit's tokens (`kitCss` in `parts/shared.js`: `--rf-quiet`, `--rf-faint`, `--rf-hair`, `--rf-line`, `--rf-wash`, `--rf-mono`, colours mixed from the text colour) instead of new numbers, and the three placement rules: the bullet says what a row is, a mark before a link says what it points to, anything after the text says what the block holds. Check "Tried and rejected" in `docs/history/DECISIONS-AND-RULINGS-2026-10-24.md` before proposing a look, and the grammar in `docs/LAYERS.md` section 2.
- **Warnings.** Use the part's `warnOnce(message, …)`; a message is written once per session, with the part's prefix, and every message is listed by **Copy warnings** (troubleshooting box). A screen updater that throws five times is retired for the session by the watcher itself (`updaterFailed`); write updaters so an empty `querySelectorAll` result is a quiet no-op, never an error.
- **Settings.** Every setting belongs to a part: add it to the `settingsSchema` of the part it belongs to (each part holds its own section; `main.js` holds none; a shortcut is a setting of its part, gathered in the window's Shortcuts section from the command register), with a plain description that says whether it applies at once (“Applies right away.”) or after a reload (“Applies after you reload the plugin.”; a heading may say it for its whole section). The core joins the parts' schemas in the order of `PART_FILES`, reads every setting through `setting(key)` (any part may read any setting) and says “reload” when a reload-only one changes. A section's heading names its umbrella group in the settings window and its place in it (`group: 'reading'`, `rank: 2`); the window's pictures and captions stay in `parts/settings-panel.js`.
- **A name from the core or another part.** A part takes what it needs in `start()` through `take(core, names)`, which looks in the core and in `core.provided` and warns once per missing name: a reload with a quiet console means the contract holds. What `main.js` still owns is listed in `publishCore()`.

### What Logseq 2.0.2 does that the code must respect

- A page link's press is ignored when the event target is the `<a>` itself (`frontend.util/link?` is true for `A` and `BUTTON`), so anything that must be clickable is drawn on `a > span:first-child::before`, never on `a::before` (the `#` of a tag-page link and the dot of a labelled block link both learned this).
- The editor shows a link to a page by name and a link to a block as `[[uuid]]`; saved text stores both as ids. Anything that maps the editor's text onto the saved text has to treat the two differently (0.2.127; the old `toSavedRange` went with the editor part at 0.4.357).
- A tag typed in a block's text is drawn as plain `<span>#Tag</span>`; only side tags and property values are `a.tag`.
- A link to a file in the assets folder is drawn with `data-href` and no `href`; the asset block's own row carries `data-url` as well.
- Navigating to an alias opens the original page. A Node embed is an empty block with `:block/link` → target, drawn as `.embed-block`; `{{embed}}` is deprecated.
- The Linked references list measures its rows: use `padding`, not `margin`, on a source-page group, or the bottom of the list is cut off. Its rows are drawn late (a probe needs about 7 s after a reload).
- Blocks inside a reference are also `.ls-block[level="0"]`; anything that counts references must leave out blocks that sit inside another block of the same group.
- A sidebar navigation link's text runs name, shortcut and count together ("FlashcardsGF2"); match the parts, not the whole.
- Pressing a query result's fold arrow in list view is a database write (collapsed state); pressing Logseq's controls is "a click", with everything a click does.
- `DB.onChanged` gives no change details (`txData` is empty); `datascriptQuery` runs in the worker, so a long query delays what it draws but does not freeze the screen.
- A plugin command registered with `logseq.App.registerCommand('global', …)` gets no palette entry (the SDK's placement "simple"); `registerCommandPalette` gets one. The troubleshooting tools use the first, behind the one palette entry **Refinements: troubleshooting**.
- `logseq.App.invokeExternalCommand('logseq.go/search')` opens search but Logseq then logs a DataCloneError about a reply it cannot clone; press the Search button instead.
- English labels the plugin still depends on: "Set property" (Add tags), "Show/Hide properties", "(Dev) …", "Page graph" (sidebar tidy), the "P n" of a PDF citation label.

### The development loop

1. Edit the file of the area (see "Where the code is"). For scripted edits use system Ruby with explicit UTF-8 (`LC_ALL=en_US.UTF-8 /usr/bin/ruby -E UTF-8:UTF-8`) and make each replacement raise unless its anchor is found exactly once. Node is installed (v24 on 2026-10-24), with `jsdom` and Playwright's Chromium in `node_modules/` (git-ignored; `npm install --no-save --no-package-lock jsdom playwright` brings them back), and `/usr/bin/python3` (3.9) writes the seeds.
2. `sh tools/check.sh`: syntax of every file through JavaScriptCore (`tools/check.js` wraps a file in `new Function('logseq', 'window', src)`), no `TEMP-DEV` block left, `package.json` and the README's version line agree, the settings and `window.*` counts printed, every file in `parts/` listed in `PART_FILES` and the reverse. With node and jsdom (both on the owner's Mac) it also runs the pretend-window tests, the boot test first (`tools/boot-test.js`: the plugin loaded into a pretend Logseq window with a stand-in `logseq`, started, its hooks fired, unloaded, and a second copy loaded over a first the way a Reload does; it fails on any warning, any error and anything left on screen), each feature's own test, the parts-apart and leaning checks, the model test, the tag map's timings and the frame and picture tests in Chromium, and the checks against the real Illness Test Graph through the command line; last, `tools/docs-check.sh`. `docs/STATE.md` section 3 lists them with what each guards.
3. Reload the plugin: `t` then `p` (Plugins panel), **Reload** on the plugin, close the panel; or, in the devtools console (`Cmd+Opt+I`), click the console prompt and run `await LSPluginCore.reload('logseq-db-refinements')`. `View > Reload` reloads the window but does not pick up edits. If the Plugins panel still shows the old version after a Reload and the page still behaves as before, quit Logseq (Cmd+Q) and open it again: on 2026-10-18 two Reloads left 0.4.131 running over 0.4.133 on disk, and a full restart picked it up. Test in the **Illness Test Graph**, and undo every test edit.
4. Look at the result: a screenshot or zoom of the running app, and the plugin's own tools in the **Refinements: troubleshooting** box (**Check what the plugin finds on this page**, **Copy styling details of this block**, **Copy warnings**, **Take the tour**; `docs/PROCESS.md` section 2b is the tour).
5. Measure when the change touches the watcher or the database round: **Measuring** then **Copy performance report** (or `debugPerf` and `debugPerfEvery` in the settings file). For jumps and late pieces, `node tools/app-frames.js` records every tour stop in the real app with the plugin off and on (Logseq started with `--remote-debugging-port=9222`).
6. Commit one fix per commit, version bumped in `package.json` and in the version line at the top of `README.md`, with a `CHANGELOG.md` note in the plain style of the existing ones; update the README's tables when a feature or setting changes. `git -c user.name=… -c user.email=… commit` (no global identity is set). Say in the note what was seen on screen and what was only read.
7. Tag the version and push the tag (`git tag v0.4.N && git push origin v0.4.N`); GitHub builds the release zip.

### Testing without a human at the keyboard

- A temporary block appended to `main.js` (marked `TEMP-DEV`, never committed: `tools/check.sh` fails while it is there) can read instructions from the settings file at load, drive the app through the plugin API (`pushState`, `updateSettings`, `editBlock`, `insertAtEditingCursor`, `openInRightSidebar`, `invokeExternalCommand('logseq.ui/toggle-theme')`), call the plugin's own functions (the core's through `window.refinementCore`, a part's through what it provided), read computed styles and `elementFromPoint`, hook `console.warn`/`console.error` of both the plugin frame and Logseq's window, wrap `logseq.UI.showMsg`, and write results back with `updateSettings` for the shell to read. It can even reload the plugin itself (`window.parent.LSPluginCore.reload(id)`), so a run that needs several reloads can be driven by a state key in the settings. Never read code from the settings file into the block; keep it data-driven (names, selectors, page names). A settings file edited from outside is not re-read by the running plugin; only a reload reads it.
- The cleanup of October 2026 used such a probe to dump, for every link, bullet, title and property row on a set of pages (and the Todos page, the tag tree and the search window), the text, computed `text-decoration`, `color`, `background-color`, `opacity`, font weight and size, `::before` and `::after` content, and every `data-refinement-*` / `rf-*` mark, then diffed the dump against a baseline after every commit. Known noise in such dumps: the left sidebar's Recent list, Logseq's rotating keyboard tip in the search window, and whether search's "Commands" group had arrived.
- Switching a setting with `logseq.updateSettings({key: false})` exercises the same path as the settings panel; measure before, after off, after on again, and expect the first and last to match.
- A command that opens one of the plugin's own boxes returns only when the box closes: do not `await` it before reading the box; read, close (a `mousedown` on the backdrop), then await.
- Background control (`app_*` tools) cannot open right-click menus or hover previews, and cannot type at a caret (only replace a whole field); accessibility presses fire `click` without `pointerdown`, so a graph that fails with a real mouse can still seem fine from the background. From the devtools console, `logseq.api.push_state('page', {name})` opens a page, `logseq.api.invoke_external_command('logseq.ui/toggle-theme')` switches the theme, and the plugin's frame is `[...document.querySelectorAll('iframe')].find(f => /refinements/.test(f.src)).contentWindow`. Keep the display awake (`caffeinate -d -u -t …`) during timed runs; a locked screen blocks every action.
- Keep every check in one place: the probe's dumps go to the settings file; remove the `dev*` keys at the end of the session.

### Before calling anything done

- Every feature in the README's Appearance table: setting on → off → on without a reload where the README says it is live; one page kind of each (plain, tag, property, journal, Journals list, alias); light and dark; both sidebars; a narrow window; the right sidebar.
- Every command from the palette, the shortcut and the bullet menu, including its refusals; the troubleshooting box and each tool in it.
- No console lines from the plugin; no errors from Logseq caused by a plugin call; **Copy warnings** says none.
- Three reloads in a row: nothing doubled, no leftover marks.
- After a Logseq update: run **Check what the plugin finds on this page** on a page, a journal and a tag page; a zero beside something you can see is a renamed part. Update `CHECKED_WITH` (in `parts/model.js`) when the plugin has been checked against the new version.

## Part 2: the command line (`~/.local/bin/logseq`)

### What it is good for

- Reading and changing the test graph while the app has it open: `logseq query -g "Illness Test Graph" --query '[:find …]'`, `logseq show --page "…"`, `logseq list page|tag|property|node|asset`, `logseq upsert block|page|tag|property|task|asset`, `logseq remove page` (recycles unless `--force`).
- Trying a Datascript query before putting it in the plugin: the plugin's own queries paste in unchanged.
- Seeding examples the plugin needs (tags with properties, journals, assets, queries, embeds) without typing in the app.

### How to write things so they come out right

- **Entity ids in queries:** `:db/id` cannot be a datom attribute in `:where`; bind ids with `:in $ ?id` / `[?id ...]` and `--inputs '[123]'` / `--inputs '[[1 2 3]]'`.
- **Links to blocks:** write `[[<uuid>]]`. Writing `[[Block title]]` makes a new *page* of that name (then recycle it: `remove page`).
- **Tags:** `--update-tags '["Name"]'` for your own tags. Built-in classes (PDF Annotation, Query through `update-properties` works, but `:block/tags [179]` does not) cannot be set from the CLI; a real PDF highlight has to be made in the app.
- **Tag structure:** `upsert tag --name X --add-properties '["prop"]'`; "extends" through `upsert page --id <tagId> --update-properties '{:logseq.property.class/extends [<parentId>]}'`; bidirectional properties through `{:logseq.property.class/enable-bidirectional? true}` on the tag's page. `upsert block` refuses a page id ("source must be a non-page block"); use `upsert page --id`.
- **Choices, icons, positions:** `upsert property` cannot add choices or a position (do it in the app); a choice's icon can be set with `upsert block --id N --update-properties '{:logseq.property/icon {:type :tabler-icon :id "Todo"}}'`.
- **Dates:** Scheduled and Deadline take milliseconds; a Date-type property takes a journal page (`[:build/page {:build/journal 20261012}]` in a seed, the journal's id through the API).
- **Queries:** a query block is `--update-tags '["Query"]' --update-properties '{:logseq.property/query "(page \"name\")"}'`; it opens in table view, and the view type switch has to be made in the app for fold-all to have arrows.
- **Embeds:** `upsert block --content " " --update-properties '{:block/link <targetId>}'` (content is required; a single space keeps the block empty-looking).
- **Same-title pages:** `upsert page --page X --update-tags` adds the tag to the existing page; a second page with the same title cannot be made from the CLI.
- **Assets:** `upsert asset --path file.pdf --target-page "…"` copies the file into the graph's `assets` folder under its new uuid and makes the asset block.
- **Chunk EDN imports.** `graph import --type edn` parses at roughly a minute per megabyte and its worker is shut down before a large file finishes ("fetch failed"); split a seed into files under 1 MB (300 KB took 10–40 s each), order them so every uuid reference points at an earlier file, and import them in sequence, stopping on the first `Failure`. Sets in EDN (`#{…}`) must not repeat an element.
- **Graph ownership.** The app lists only graphs it created or opened itself; a graph made by `graph create` is invisible to it (make the graph from the app's "Create a new graph" dialog instead, then import into it). An import must own the graph's server: switch the app to another graph first, or it fails with `server-owned-by-other`. **After any import or long CLI session, run `logseq server stop --graph "<name>"` before opening the graph in the app** (`logseq server list` shows `owner-source`: `cli` or `ele`). A graph whose worker the CLI still owns opens in the app but is unusable with a real mouse (no unfold, no selection, no zoom); the fix is that stop, then View > Reload.

### Shell habits that saved time

- `tr -d` strips every listed character wherever it appears (it mangled a uuid containing `d`); extract uuids with `grep -o '[0-9a-f-]\{36\}'`.
- `grep -c` exits 1 when the count is 0, which ends an `&&` chain; put such counts last or outside the chain.
- Long-running imports go in the background with a waiter that stops on both the success line and `Failure|Error`; silence is not success.
- Keep a `PROGRESS.md` in the scratchpad while a long session runs: which fixes are committed, what the graph gained, what settings were changed and must be put back.
